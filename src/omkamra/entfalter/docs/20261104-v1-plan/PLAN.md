# Entfalter v1 implementation plan

This document specifies the intended architecture and milestone scope for refining `omkamra.entfalter` into a generic, extensible discovery and realization engine. It is a planning document: the ordered implementation phases, durable design decisions, and progress diary will be recorded separately after the plan has been reviewed.

## 1. Goals

Build a generic graph/node compiler and executor which can:

- describe discoverable and realizable host state as declarative Clojure node specifications;
- discover a Linux server through Python scripts generated by `omkamra.pygen`;
- realize desired state through the same node model and generated Python;
- execute many hosts in parallel while respecting dependencies between hosts;
- fail loudly and immediately on errors;
- make it straightforward to add further node kinds later.

The first concrete end-to-end result is a Debian/systemd server description sufficient to reproduce the following:

- the kernel hostname;
- the FQDN;
- the ordered `/etc/hosts` contents relevant to the managed state;
- the names of installed packages.

V1 also requires a targeted configuration-graph fixed point: discovering an existing desired graph against a matching target, serializing and deserializing the discovery artifact, and materializing it must reproduce the canonical configuration graph for that graph’s managed scope.

Realization ensures every desired package name is installed, but does not remove extra packages. Package versions and pinning are out of scope for v1.

## 2. Scope and non-goals

### In scope

- Debian operating-system discovery.
- systemd/init-system discovery.
- Generic node specifications with Malli input/output schemas.
- Discovery and realization lowerings selected by context-aware Clojure multimethods.
- Automatic injection of required fact nodes.
- Dependency graph construction, cycle detection, stable node identities, and deduplication.
- Same-run invalidation based on declared `:changes` and `:affected-by` keywords.
- Compilation of execution units to Python via pygen.
- JSON stdin/stdout protocol for each execution unit.
- Parallel execution of independent units, including cross-host dependencies.
- A narrow SSH connection schema using Apache SSHD and SSH-agent authentication.
- Passwordless `sudo` when the target user is not root.
- Serialization and later materialization of discovery-generated node-instance EDN for realization.

### Deferred

- Non-Debian distributions.
- Non-systemd init systems.
- Broad systemd configuration and call-graph discovery.
- Service-specific configuration beyond the initial hostname/package example.
- Package removal, package versions, pinning, repositories, and package-manager policy.
- Authentication methods beyond the initial SSH-agent path.
- Cross-run execution caching or persistent execution history.
- Embedding generated Python source in discovery output.

The architecture must allow these features to be added incrementally without changing the core graph/execution model.

## 3. Conceptual model

### 3.1 Node specifications

A `defnode` macro binds a declarative node specification to a Clojure Var. A node specification describes a kind of state/computation, not one observed instance. It declares:

- named input ports and Malli schemas, including required/optional inputs;
- named output ports and Malli schemas;
- instance cardinality per host, such as `:one` for hostname or `:many` for vhosts;
- semantic requirements, initially expressed as namespaced node keywords;
- potential state changes, expressed as arbitrary keywords in `:changes`;
- change effects that may invalidate this node, expressed as arbitrary keywords in `:affected-by`;
- enough identity/parameter metadata to derive stable instances and deduplicate equivalent work.

A node kind may support one or more lifecycle capabilities:

- `:discover`, which observes state and produces JSON-compatible outputs;
- `:materialize`, a Clojure-side graph transformation which converts discovery outputs, including outputs from required nodes, into zero or more configuration node instances and dependencies;
- `:realize`, which ensures desired state and produces outputs plus actual changes.

`:discover` and `:realize` are executable operations lowered to Python. `:materialize` is not lowered to Python. Discovery-only and realization-capable nodes are all ordinary `defnode` declarations. There is no separate probe-node or discovery-node abstraction. A node that does not support a requested capability must fail loudly. A node directly targeted for `:realize` must support `:realize`, but a discovery-only node may be an implicit prerequisite of a realization target and is then scheduled with `:discover`.

Node-type `:requires` references are resolved to concrete node instances during graph compilation, not macro expansion. Requirements are operation-neutral and the planner resolves their operation from the current root operation and the required node’s capabilities. In a `:discover` run, required nodes use `:discover`; a required node with no `:discover` capability is an error. In a `:realize` run, a required node uses `:realize` when available, and falls back to `:discover` when it is discovery-only. The fallback discovery runs in the realization workflow as a prerequisite and its outputs remain runtime support state. A required node supporting neither operation is an error.

The same `:requires` declarations provide discovery recipes for targeted configuration-only nodes. If a target supports `:discover`, it may be observed directly. If it supports `:materialize` but not `:discover`, the planner recursively discovers its required nodes and materializes the target from those observations; the target itself is not executed with `:discover`. A targeted node with neither direct discovery nor materialization supported by discoverable requirements is an error. The final graph therefore contains instance references, allowing a particular vhost instance to depend on the particular load-balancer configuration instance created alongside it. Unknown references and invalid node declarations are compilation errors.

### 3.2 Graphs and hosts

A `defgraph` macro binds an instantiated graph value, normally built by threading an empty graph through node-type-specific helper functions:

```clojure
(defgraph web-config
  (-> (graph)
      (set-hostname "web-1")
      (ensure-packages ["curl" "rsnapshot"])))
```

Users can write helper functions to parameterize graph construction. A `defhost` macro evaluates its graph expressions and binds the resulting canonical configuration graph. The result is pure, serializable graph data without connection or authentication details; graph-building helpers are evaluated while constructing that value. Its `:graphs` expressions may include calls to graph-building helpers:

```clojure
(defhost web-1
  {:graphs [web-config (make-web-graph {:vhosts [...]})]})
```

The resulting configuration graph already contains concrete canonical node instances for each bound host. Host graphs are independent unless a node explicitly depends on a node instance belonging to another host. Connection details are supplied only to execution functions.

### 3.3 Node instances

A canonical configuration node instance is a serialized occurrence of a node kind for a particular host and parameterization. It contains only:

- a stable configuration identity;
- host identity;
- node kind identity;
- desired JSON-compatible inputs;
- configuration-level dependency references.

Runtime execution state is separate. An execution record refers to a canonical node by identity and contains the selected operation, resolved runtime inputs, execution status, actual JSON-compatible outputs, actual changes, lowering/unit metadata, and other transient execution data. Discovery-artifact records may serialize observed outputs, but those outputs do not become part of the canonical configuration node.

Each node type may provide a pure `node-identity` multimethod implementation. It receives the node type, explicitly supplied inputs, resolved upstream inputs, and static compilation context, and returns a deterministic unique string within that node kind and host. It may not depend on the node’s own runtime outputs. The final stable identity is derived from host, fully qualified node kind keyword, and this identity string. The fully qualified node keyword is sufficient as the node-type compatibility identity; v1 does not add a separate version field.

Evaluating a `defhost` declaration produces a canonical configuration host graph, and a materialized discovery result uses that same configuration-graph EDN shape. Both contain concrete node instances, stable configuration identities, desired inputs, and configuration-level dependency references. Raw discovery returns a separate serializable discovery-graph artifact containing discovery node instances and observed outputs; it is not directly suitable as input to `realize!`. The complete canonical host graph and separate runtime execution state remain on the Clojure side in persistent data structures during execution; neither is embedded in generated Python. Aggregated views such as a host summary are calculated separately from the node instances.

The canonical configuration graph must exclude transient discovery provenance, execution metadata, observed-output fields, and runtime change reports that would prevent equality with the configuration graph produced by evaluating `defhost`. `canonical-config` removes those runtime-only fields, normalizes node instances by stable identity, orders dependency references deterministically, and applies node-specific normalization to semantically unordered values. For example, package-name collections are normalized as set-like values, while ordered `/etc/hosts` entries retain their order. Equality after canonicalization is ordinary Clojure equality. If provenance is retained separately, `canonical-config` must project both graphs to the same comparable configuration representation.

Discovery has an explicit scope. Open-ended discovery, started without a desired configuration graph, may materialize an inventory of all state represented by its discovery roots. Targeted discovery, started with an existing configuration graph, must retain the target graph’s managed node identities and materialize only that managed scope; injected discovery-only fact nodes are supporting observations and must not widen the materialized configuration graph. In targeted mode, every emitted configuration-node identity must already belong to the target graph’s managed scope; an out-of-scope emission is a loud error. V1 has no implicit targeted scope expansion. Open-ended materialization may emit derived inventory nodes.

A pure materialization step converts the saved discovery artifact into the canonical configuration host graph. Targeted materialization receives the target configuration graph as its scope and can then pass the resulting graph directly to `realize!`; open-ended materialization may instead produce an inventory graph from discovery roots. A realization lowering consumes materialized instance inputs as desired state, while observed outputs may be retained as provenance/current-state information outside the canonical configuration graph. Both artifacts contain only portable declarative data and fully qualified node keywords; they contain no Vars, functions, connection details, or generated Python source.

Compilation derives a separate execution graph from the canonical configuration graph. Static compilation resolves node Vars and requirement declarations, while incremental planning expands injected discovery-only nodes, resolves concrete execution dependencies as inputs become available, selects lowerings, and partitions each planning wave into execution units. The execution graph is not the serialized configuration graph and is not the result of `defhost` or `materialize`.

## 4. Graph compilation

Compilation should proceed in explicit static stages:

1. Validate the canonical configuration graph, node declarations, cardinality, and node input parameters.
2. Qualify symbolic node references deterministically; resolve node Vars and requirement declarations.
3. Expand required nodes recursively and resolve each required instance’s operation from the root operation and its capabilities. A realization target may introduce discovery-only prerequisite instances scheduled with `:discover`; a targeted configuration-only discovery target uses the same expansion as its discovery recipe. Users need not write fact-collection nodes explicitly, but may do so when desired. Reuse an already available valid discovery result instead of executing the same prerequisite again.
4. Validate canonical node instances and their explicit inputs, enforcing `:one`/`:many` cardinality.
5. Resolve statically known cross-host instance references.
6. Detect cycles across the complete multi-host graph.
7. Initialize runtime execution state for every node, including execution status and any already available inputs.

Static compilation does not require all runtime facts to be available and does not emit one permanent execution plan. The engine incrementally compiles the current execution state into the next executable wave. Each wave may:

1. identify ready nodes whose dependencies and runtime inputs are available;
2. compute execution identities and context-aware lowering keys;
3. dispatch discovery or realization lowerings;
4. deduplicate equivalent work and fuse compatible nodes into units, minimizing SSH/Python execution units;
5. emit one or more standalone Python units for the wave;
6. execute the wave and merge its outputs and actual changes into runtime execution state;
7. invalidate affected nodes conservatively and repeat until all required nodes have completed.

Missing lowerings, unavailable required context, deadlocks, and unit failures are loud errors. The canonical configuration graph remains unchanged throughout execution; runtime outputs, statuses, and changes belong to the separate execution state.

The discovery workflows are separate from this general compilation pipeline:

- `discover-hosts!` takes a connection resolver and explicit host IDs, creates the v1 default set of discovery root node instances—ordinary `defnode` instances whose `:requires` recursively expand the discovery graph—and compiles and executes that graph with open-ended scope;
- `discover-graph!` takes a connection resolver and an existing configuration graph, uses that graph’s node instances as discovery targets, records those target identities as the managed scope, and expands the discovery requirements needed to observe them.

Both functions return the executed discovery graph as a serializable artifact, including enough scope information for later materialization. Materialization is a separate post-discovery operation used only when converting that artifact into a configuration graph.

The graph compiler should preserve a clear distinction between:

- declarative node definitions;
- canonical configuration graphs produced by `defhost` or `materialize`;
- compiled execution graphs with resolved requirements and injected nodes;
- executable units;
- execution results.

## 5. Specialization and lowering

Lowering is implemented in Clojure multimethods, not serialized into discovery output and not represented as handwritten Python in node definitions. Dispatch must be able to inspect a context map, including facts such as operating system and init system.

Lowering dispatch must be able to specialize on validated user inputs as well as platform context. The protocol should be conceptually equivalent to:

```clojure
(defmulti lowering-key
  (fn [node operation context]
    (:kind node)))

(defmulti lower-node
  (fn [node operation context]
    [(:kind node)
     operation
     (lowering-key node operation context)]))
```

`node` contains validated explicit inputs and resolved upstream inputs. `lowering-key` returns a compact, intentional specialization key rather than dispatching directly on an arbitrary input map. The planner computes it only after the node’s required upstream inputs are available. Missing lowering keys or lowering methods are loud compilation errors.

The exact method return protocol remains an implementation detail, but it must provide pygen-compatible forms for the node’s work and declare the JSON values it produces/consumes.

The first specializations are Debian and systemd implementations. Adding another OS or init system should mean adding node/lowering definitions rather than rewriting the scheduler or unit protocol.

### Discovery materialization

Discovery and realization use the same `defnode` declarations, but discovery may execute internal discovery-only node instances which do not belong in the final configuration graph. Materialization is a pure reducer. Targeted materialization reduces target nodes in deterministic configuration-graph order; open-ended materialization reduces discovery nodes in deterministic dependency order. When multiple nodes are ready, stable node identity provides the tie-breaker:

```clojure
(defmulti materialize-node
  (fn [config-graph target-node discovery-node discovery-graph context]
    (or (:kind target-node)
        (:kind discovery-node))))

(defn materialize-targeted
  [discovery-graph target-graph context]
  (reduce
    (fn [config-graph target-node]
      (materialize-node config-graph target-node nil discovery-graph context))
    (empty-config-graph target-graph)
    (deterministic-configuration-order target-graph)))

(defn materialize-open
  [discovery-graph context]
  (reduce
    (fn [config-graph discovery-node]
      (materialize-node config-graph nil discovery-node discovery-graph context))
    (empty-config-graph discovery-graph)
    (deterministic-topological-order discovery-graph)))
```

The public `materialize` operation has two pure arities:

```clojure
(materialize discovery-graph)
(materialize discovery-graph target-config-graph)
```

The one-argument form performs open-ended inventory materialization. The two-argument form performs targeted materialization using the supplied configuration graph as scope. Internal reducer helpers may receive a derived materialization context, but public callers do not supply runtime context.

Each `materialize-node` method receives the current persistent configuration graph, an optional target node, an optional current discovery node, the complete discovery graph, and planning context. In targeted mode, the target node defines the output scope, its materializer may combine any number of discovery observations, and every emitted identity must be in that scope. The target may be observed directly or reconstructed from discoverable `:requires` nodes; a materializer is required for the latter case. In open-ended mode, the discovery node defines the inventory output and may produce derived nodes. A method may return the graph unchanged or add zero or more configuration node instances and dependencies. This supports one-to-one, one-to-many, and no-op materialization, with one-to-many output applying to open-ended or explicitly scoped results. General incremental many-to-one partial-definition merging is not part of v1. Each reducer processes its original input nodes only; nodes added by a materializer are configuration outputs and are not recursively fed back into the same reduction. Chained transformations require explicit materialization phases.

Added nodes are deduplicated by stable identity. Equivalent definitions merge only when their canonical contents agree; conflicting definitions for one identity fail loudly. Materialization context must be pure and derived from the discovery artifact and static planning data, with no SSH, clock, or other runtime side effects. A separate pure `materialize` operation applies these multimethods to a saved discovery artifact; in targeted mode it also receives the target configuration graph. Discovery-only instances remain in the raw artifact but are omitted from the materialized configuration graph. The completed graph and all added dependencies are validated after reduction. Ordinary `defhost` and `realize!` compilation bypass this step.

For targeted discovery, materialization must satisfy the fixed-point invariant that a matching target produces a configuration graph canonically equal to the original desired graph within the recorded managed scope. In particular:

```clojure
(= (canonical-config desired)
   (-> (discover-graph! resolver desired)
       serialize
       deserialize
       (materialize desired)
       canonical-config))
```

This invariant assumes that the target already satisfies `desired`; it does not require open-ended inventory materialization to equal an absent desired graph. Serialization and deserialization of the discovery artifact must not change the result. After the fixed-point comparison succeeds, realizing the materialized graph against the same target must report no actual changes; the complete discover → materialize → realize cycle is idempotent.

## 6. Execution units and protocol

Each execution unit is a generated Python script. Its protocol is:

- read one JSON object on stdin containing only the unit’s required values;
- perform its work;
- write one JSON object on stdout containing an `outputs` object and a `changes` array;
- write diagnostics to stderr;
- exit nonzero on any error.

Unit inputs and outputs are grouped by unit-local node aliases and ports, rather than serializing the complete host graph:

```json
{"inputs": {"n0": {"os-id": "debian"}}}
```

The Clojure planner maintains the alias-to-node-instance mapping and merges returned outputs into runtime execution state, not into the canonical configuration graph. Runtime state records at least each node’s status, available outputs, actual changes, and execution metadata. The `changes` array contains canonical keyword strings without a leading colon, such as `"my.ns/hostname"`. It is required to be a subset of the node type’s declared potential `:changes` keywords. Discovery units normally report no changes; realization lowerings report the changes that actually occurred.

A planning wave contains one or more units whose inputs are available and whose dependencies permit concurrent execution. Independent units, including units for unrelated hosts, are executed in parallel over persistent SSH connections per host. The engine waits for the wave’s results, merges them into runtime execution state, applies invalidation, and compiles the next wave. A failed unit prevents newly schedulable dependent work from being started, while already-running independent units may finish. The overall run fails and must not produce a successful discovery or realization result. Cross-host dependencies participate in the same global DAG: a failure in host B propagates to dependent work for host A, while unrelated host graphs remain independent.

The runtime loop terminates successfully only when no pending or invalidated nodes remain. If no executable wave exists while required work remains, the engine fails with a dependency deadlock or missing-context error.

## 7. Same-run deduplication and invalidation

Deduplication applies within one execution run only; there is no v1 persistent execution cache.

Equivalent injected nodes should execute once when their node kind, specialization, parameterization, and input bindings are provably equivalent. Dynamically computed parameters are ordinary graph inputs. Shared upstream outputs therefore make equivalence explicit; opaque values must not be deduplicated without a provable identity.

Nodes declare arbitrary potential-change keywords in `:changes` and arbitrary effect keywords in `:affected-by`. `:requires` expresses structural/data dependencies and execution ordering; it does not by itself mean that every state change from the required node invalidates the consumer. If an upstream realization node reports an actual change, the planner records a scoped change event containing at least the host, source node identity, and change keyword. Change matching is host-local by default: a node is marked invalidated in runtime execution state when a same-host event intersects its `:affected-by` set. Cross-host invalidation requires an explicit cross-host dependency or scope. A consumer may also be invalidated when a value from a `:requires` dependency that it actually consumed changes.

The runtime must detect non-convergence by recording the effective execution state for each completed or invalidated node, including its operation, input fingerprint, and relevant runtime state. If the same node is scheduled again with the same effective state without new relevant progress, the run fails as non-converging. The optimization must conservatively preserve correctness when equivalence or change impact cannot be proven. Runtime statuses include at least `:pending`, `:ready`, `:running`, `:succeeded`, `:failed`, and `:invalidated`.

## 8. SSH and privilege model

The initial connection schema is intentionally narrower than all Apache SSHD capabilities:

- target hostname and port;
- target user;
- SSH-agent authentication through Apache SSHD;
- timeout and host-key policy fields as needed by the existing SSH layer, with host-key verification enabled by default.

Connection resolution is supplied separately to `discover-hosts!`, `discover-graph!`, and `realize!` as a function from host identity to connection configuration. V1 includes an adapter which resolves connections from a map. Connection data is never part of `defhost` values or serialized host-graph EDN.

If the target user is not root, generated commands must use non-interactive passwordless `sudo`. Before scheduling the first mutating realization unit for a host, the engine must preflight the required privilege path on that host’s persistent SSH connection, using non-interactive `sudo` validation. A failed preflight prevents mutating realization work for that host. Discovery operations that require privilege must perform the same validation before their first privileged unit. Discovery/realization must fail before making a partial claim of success if the required privilege path is unavailable.

The schema should be designed so additional Apache SSHD authentication and connection mechanisms can be added later without changing graph or unit semantics.

## 9. Initial node library

The initial library should include:

- Debian OS identity/facts node;
- systemd/init-system node;
- hostname node with outputs for kernel hostname, FQDN, and ordered `/etc/hosts` state;
- installed-package-name node producing package names only.

The hostname and package nodes must each support discovery and realization. The hostname node manages the kernel hostname, FQDN, and one canonical `/etc/hosts` entry while preserving unrelated lines. Package realization installs missing desired names and leaves unrelated installed packages untouched.

Broader systemd unit inventory, changed-file analysis, call-graph construction, and service-specific inspection are architecture-guided follow-on additions, not v1 acceptance criteria.

## 10. Validation and testing

The implementation must include tests for:

- macro-produced declarations, deterministic namespace qualification, and deferred symbolic resolution;
- Malli validation of node ports, cardinality, graph declarations, host declarations, node input parameters, and JSON unit boundaries;
- requirement injection, default discovery roots, and missing-node failures;
- deterministic reducer-based discovery materialization, including one-to-many open-ended rewrites, target-scope enforcement, target materializers combining multiple observations, stable deduplication, conflicting-definition failures, and omission of internal discovery-only instances;
- context-aware specialization dispatch and loud missing-context failures;
- stable instance identity and conservative deduplication;
- cross-host dependency edges and cycle rejection;
- host-local `:changes`/`:affected-by` matching, explicit cross-host invalidation, direct consumed-output invalidation, and same-run change invalidation;
- incremental planning waves, runtime status transitions, replanning after outputs, and repeated-state non-convergence detection;
- unit partitioning at lowering-decision boundaries;
- generated Python syntax and JSON stdin/stdout behavior;
- immediate failure propagation and independent parallel host execution;
- per-host privilege preflight before privileged discovery or mutating realization;
- Debian/systemd hostname discovery and realization;
- package-name discovery and install-only realization;
- discovery-generated EDN being saved and later materialized;
- saved discovery EDN being materialized through the reducer and round-tripping into realization;
- targeted configuration-graph discovery fixed-point verification, including managed-scope preservation, serialize/deserialize round-tripping, canonical normalization, and equality;
- realization idempotence after discover → materialize, with no actual changes reported on the subsequent realization;
- discovery-only nodes being allowed as `:discover` prerequisites of realization targets;
- configuration-only targets being reconstructed from discoverable `:requires` nodes;
- discovery-only prerequisite results being reused across discovery and realization work when valid;
- discovery-only nodes being rejected when directly targeted for `:realize`.

Tests should use the running development JVM for Clojure-side work, and execute generated Python only as the target runtime being tested. Real SSH integration should be isolated from pure graph/compiler tests and use a controlled test target or fixture.

## 11. Completion criteria

V1 is complete when:

1. A user can define reusable node kinds, graphs, and hosts with the planned macros, without embedding connection details in host values.
2. A Debian/systemd target can be discovered through generated Python units over SSH-agent authentication using a separately supplied connection resolver.
3. The result is a serializable discovery-graph EDN artifact containing ordered node instances with JSON-derived outputs and no embedded Python, Vars, functions, or connection details.
4. The saved artifact can be materialized into the canonical configuration host graph and fed directly to realization, reproducing hostname, FQDN, `/etc/hosts`, and ensuring the discovered package names are installed.
5. Targeted discovery of an existing configuration graph against a matching target, including managed-scope preservation and artifact serialization/deserialization, produces a canonically equal configuration graph; realizing that materialized graph against the same target reports no actual changes.
6. The engine incrementally plans and executes parallel waves, preserving correct cross-host dependency handling and replanning after outputs and changes.
7. Graph cycles, unresolved references, unsupported lowerings, missing context, privilege failures, and unit failures are loud and fail-fast.
8. Adding future OS/init/service nodes does not require redesigning the graph compiler, unit protocol, or scheduler.
9. Existing Entfalter APIs may be replaced where they do not fit this model; preserving the current script-emission/reconcile API is not a v1 requirement.
